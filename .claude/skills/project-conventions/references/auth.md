Supabase, passwordless email code (+ magic link) — backend auth reply 2026-09-27. `lib/vendor/supabase/` is the only importer of `@supabase/*` (vendorSeams). Session in cookies via `@supabase/ssr`, refreshed in `src/proxy.ts`; never localStorage. The proxy also passes the verified user id to the render (`x-ef-session`, always overwritten; a chrome hint, never authorization) and the root layout seeds `useSession` with it, so the first paint has the member or guest chrome (failure log #37). A failed check sends no hint (the browser decides). Trade-off, accepted (product 2026-09-30): reading it in the root layout renders every page per request, no static prerender; pages fetch in the browser anyway and warm LCP matched main. `http.ts` middleware sends `Bearer`, refreshes once on 401, else signs out. Viewer from `GET /api/v1/me`: 401/none → guest, first sign-in creates the account (backend PR #238): **404 → `unlinked`** (token without email, or deleted account), **409 `/problems/account-exists` → `accountExists`** (email belongs to an existing unlinked account: "contact support"), goal → mentee, approved `mentor_profile` → mentor; never `primary_role`. Query keys carry the session identity (signed-in lists differ). Post-sign-in destinations go through `safeReturnTo` (local paths only). **Google** is offered too (user, 2026-10-03): `signInWithOAuth({provider:'google'})` from the vendor seam, landing on the same `/auth/callback` as the magic link — one PKCE exchange serves both. The callback is **told** which way in it was, by `from=google` on the landing URL (`_auth/failureReason.ts`): the error codes cannot say, because Supabase answers an expired or reused email link with `access_denied` too, and reading that as "cancelled at Google" loses the 6-digit-code advice that is the only help on that screen. With `from=google`: `access_denied` is the person cancelling (`google_cancelled`), anything else — including a code that would not exchange — is `google_failed`. Without it, `link`. `mode=signup` sends a failure back to /signup rather than answering a half-finished sign-up with "New here?" on the log-in page, and the screen drops `?error=` from the address bar once the notice is read. Other ways in are offered through `EmailCodeForm`'s `alternatives` slot, which shows on the **email step only**: leaving for Google once a code is on its way would throw away the typed code and the 60-second resend timer. Google is also the first way a visitor can reach `409 account-exists` without ever typing their address. Password: backend WIP, not offered

## Sign up and log in (Sign In.dc.html, from 2026-10-17)

The paragraph above predates the rebuild; where they differ, this wins.

- **Passwordless only, one flow for both entries.** `/signup` (`?role=mentor` shows the mentor page), `/login`. `signInWithOtp` with `shouldCreateUser: true` serves both: an unknown email at log-in gets its code, then the finish step. The emails carry the 6-digit code only (Supabase templates: Magic Link for log-in, Confirm signup for new accounts; owner set them, with code length 6, expiry 600 s and a 30 s gap). `AuthScreen` → `useSignInFlow` → `SignInForm` (props only).
- **Who just signed in:** `fetchSignInAccount()` reads `GET /me` outside the query cache. `first_name === null` means never named (owner decision, no extra field): name them from the sign-up field, Google's given/family names (from the Supabase identity), or the finish step, through `useSaveName` (`{ fullName }` → `full_name`, backend #476 splits; `{ firstName, lastName }` → the two fields). The name is saved before the redirect; a failed save shows the finish step with the error, and the session stays.
- **Where they go** is `signInOutcome` (`app/_auth/outcome.ts`, PRD rev 9): returning → a checked `next`, else the account's home (`homeFor`; a mentor whose `approval_status` isn't `approved` → `MENTOR_REVIEW_HOME`, `/mentor-application` once mentor onboarding is on, else `/dashboard`). A new account → `newAccountDestination`: with `NEXT_PUBLIC_ONBOARDING_V5_ENABLED=true` always the `/onboarding` entry, which opens the mentee or mentor page by role and keeps the query (`role=mentor` for a mentor sign-up, `for/sid/time` for a booking from PR 4; agreed with the onboarding session). With it off: a mentor → `/onboarding/mentor` when `NEXT_PUBLIC_MENTOR_ONBOARDING_ENABLED=true`, else `/home`; a mentee → `next`, else `/home`. Every outcome shows the toast for 1.4 s first. Role comes from the account; the page's role only marks a brand-new mentor sign-up.
- **Google** returns through `/auth/callback` to the screen it started on (`auth=google`, plus `mode`, `role`, `next`), so the screen names a new account and shows the toast. "Google is now linked" is read from the Supabase identities (a Google identity added in the last 10 minutes beside another one). A refusal comes back as `error=google_*` and shows the design's googleError with the form kept.
- **Codes:** Supabase answers wrong and expired codes alike (`otp_expired`), so a refusal 10+ minutes after the send is expired (failure log #65). Misses are counted on screen per address (`codeLock`, 5 then 15 minutes); the real guard is Supabase's per-IP limit and edufurtherbe#475. `user_banned` is the suspended step.
- **Already signed in** visitors to either page go straight to `next` or their home, with no toast.
- **Booking modal guest step** (sign-in PR 4): a guest signs in inside the modal through `SignInBookingFlow` (app/_shell), which gives `BookingFlow` a page-side controller (`useBookingSignIn`) on the same code engine as the sign-in page (`useEmailCodeAuth`). Whether a booking is a guest's is decided once, as the modal opens. Existing account → carries on in the modal ("Logged in as …"); new account → Full name, then the `/onboarding?for&sid&time` entry when onboarding is on, else carries on. Google leaves for `/mentors/{handle}?book&at` (the profile's reopen link); the sign-in screen reads that `next` as the booking (`app/_auth/booking.ts`). Every screen that books uses `SignInBookingFlow`, never `BookingFlow` directly.
